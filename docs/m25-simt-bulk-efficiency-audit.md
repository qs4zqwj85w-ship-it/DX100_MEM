# M25 — SIMT/Bulk efficiency audit: the selector, the regressions, the accounting

**Status: audit only. No source file, configuration or historical artifact was modified, and no new
simulator cell was run.** Every number below is read from an M24 artifact that predates this
milestone, through `tools/m25_extract.py` (31 M24-F pairs → `build/wm/m25/diag.csv`). Tags: [M]
measured in an existing log, [C] recomputed from measured counters, [A] analytic, [H] hypothesis.

Scope: Phase 2 (the existing compiler-directed selector), Phase 3 (why Bulk loses), and Phase 6
(reconciling prior numbers). Phase 4 is `m25-adaptive-selection-design.md`, Phase 5 is
`m25-dram-organization-audit.md`, Phase 7 is `m25-architecture-proposal.md`.

---

## 0. Summary

| Question | Answer |
|---|---|
| Is there a compiler-directed selector? | **No.** There is a *static, per-instruction class map* supplied as trace metadata, plus a hybrid driver that honours it. §1. |
| Does it work? | Yes, mechanically: M9's gates show the hybrid reproduces each pure path to the cycle, and the partition is exhaustive and disjoint. It is a dispatch mechanism, not a selector. |
| Can it choose SIMT for unsuitable workloads? | Only if the annotation says so. The annotation is one bit per instruction derived from the generator's `regular` draw, so the policy is effectively "indirect → Bulk", which is wrong on 6 of the 31 M24-F traces. |
| Can regions mix? | Per instruction, yes, within one run. Per *region* (kernel) with a boundary, no: there is no region concept, no drain/refill accounting, and no runtime re-classification. |
| What actually makes Bulk lose? | **Cache reuse, not "extra calculations".** Bulk bypasses L1 and dedups only inside a window, so it re-fetches across windows; and its index pass has a **0 % L2 hit rate** on every cell. §5. |
| Does the index-stream mechanism reduce traffic? | **No.** It converts a repeated, potentially cache-friendly index stream into one uncached linear pass. Measured `cc1` L2 hits = 0 in 23 of 31 cells and ≤ 0.05 % in the rest. §4. |
| Is the comparison fair? | Mostly yes at the request level (same R, same MSHRs, same caches, same 4/cycle issue), with three named gaps: no store path, no per-region boundary cost, and M24-F's per-client tags cannot attribute 62 % of Bulk's DRAM reads. §3, §6. |

## 1. Phase 2 — what the selector actually is

### 1.1 The mechanism, in source

| Piece | Where | What it does |
|---|---|---|
| `ClassMap` | `sim.hpp` (after `Trace`) | `std::vector<u8> cls`, one entry per memory instruction, exactly two values (`OpClass::Simt`, `OpClass::Bulk`). |
| `build_op_classes(cfg, trace)` | `workload.cpp:291` | Chooses a *source*: `"gen"` copies `Trace::instr_class`; `"pattern"` recomputes it from addresses with the contiguity rule; `"simt"`/`"bulk"` force one class. No cost model, no occupancy, no timing input. |
| `Trace::instr_class` | `workload.cpp:191` | Filled **while the trace is generated**: `regular = uni(rng) < cfg.kappa`, then `instr_class[i] = regular ? Simt : Bulk`. A file trace supplies its own per-instruction class. |
| `Sim::run()` | `system.cpp` | `if (cfg_.dispatch) return run_hybrid();` — the only fork. |
| `Sim::run_hybrid()` | `bulk.cpp:3220` | Builds the class map and the bulk workload from one `Trace`, then runs both front-ends over one `MemorySystem` and one shared `SlotPool` of `R` ids. |
| the dispatch itself | `bulk.cpp` in `run_hybrid` | `if (cm.at(i) != Simt) continue;` when collecting the SIMT instruction list. One predicate, evaluated before the first cycle. |
| `Config::op_class`, `dispatch`, `dispatch_order` | `util.cpp` | The three knobs. `op_class` names the metadata *source*, `dispatch` enables the hybrid, `dispatch_order` is a tie-break. |
| `Config::m23_select` | `util.cpp`, `bulk.cpp` | Optional audit trail: one row per instruction (`class`, `elems`, `source`, `reason`) written once, before execution. Diagnostic only. |

### 1.2 The seven questions

1. **Functional in the simulator?** Yes. `dispatch=1` runs both front-ends against one hierarchy,
   one residency budget (`SlotPool(slots, true)`) and one `mem_->tick` per cycle; M9's gates G1/G2
   require the all-SIMT hybrid to equal the pure SIMT run and the all-Bulk hybrid to equal the pure
   engine run, to the cycle and to the `completion_hash`.
2. **Generated by a compiler?** **No.** `op_class="gen"` is the generator's own `regular` bit,
   recorded at trace-build time and handed to the simulator "as if" a compiler had supplied it.
   `op_class="pattern"` recomputes the same bit from the addresses with the `kappa_real` contiguity
   rule. Neither analyses an address expression, an IR, a loop nest or an aliasing question. The M9
   design document says this in as many words ("M9 does not implement that analysis and does not
   claim to"); the code carries the same comment at `build_op_classes`.
3. **Can operations mix?** Yes, at *instruction* granularity inside one run: the class map is
   exhaustive and disjoint, every element belongs to exactly one path, and
   `simt_elems + bulk_elems == N` is asserted. There is no *region* granularity: no kernel
   boundary, no flush, no re-entry.
4. **Can it choose SIMT for unsuitable workloads?** Structurally yes — `op_class="simt"` forces it,
   and any metadata that says SIMT routes everything to SIMT. But nothing in the *policy* does:
   the metadata is the generator's regularity draw, so every indirect instruction becomes Bulk
   even when SIMT is faster. M9 measured this deliberately: HOT and DUP stay Bulk at 0.40× and
   0.61×, and M24-F shows the same for `n1_seq8m` (0.975), `qc2534` (0.843), `dubcova3` (0.837).
5. **Runtime switching overhead?** **Zero, because there is no runtime switching.** The partition
   is fixed before cycle 0 and never revisited; `run_hybrid` contains no re-classification, no
   deoptimisation and no drain-and-switch path. The one *real* cost a switching design would pay
   is measurable but is not modelled as a boundary: the Bulk path's start-up — descriptor fetch,
   index tile fill, first window seal — retires its first element at 13 212 cycles on a 4 KiB
   footprint and **64 173 cycles** (26.4 % of the whole run) on `criteo_2k` [M].
6. **Fallback when Bulk is unsuitable?** No. There is no fallback, no watchdog, no occupancy check
   and no re-execution path. A misclassified instruction is executed by the engine and its cost is
   paid; M9's report states exactly that.
7. **What would a real compiler implementation require?** See §1.3.

### 1.3 From metadata to a compiler

| Requirement | Present today | What it would take |
|---|---|---|
| recognise an indirect address expression | no | an IR pass over the loop body: `addr = base + load(idx) * width` with the load's address affine in the induction variable. Polygeist/MLIR or LLVM, not a trace generator. |
| tile the loop to the engine's window | no (`build_bulk_workload` writes one descriptor over the whole trace) | loop tiling to `batch_window`, with the descriptor emitted per tile and `elem_base` advanced. |
| prove legality | no | no cross-iteration dependence, no store to the region inside the loop, no aliasing with the index array. DX100's compiler does exactly this with MLIR alias analysis. |
| cost model | no | the policy of `m25-adaptive-selection-design.md`; needs loop-trip-count and footprint estimates, which the compiler has. |
| region boundary semantics | no | a barrier and a flush at the boundary, and an execution-model answer for stores (the model has no store path at all). |
| fallback | no | either static (when uncertain, emit SIMT) or dynamic (a bounded watchdog on the first window). Dynamic fallback needs an engine that can abort a descriptor, which exists (`abort_desc`) but is not wired to a policy. |

**Stated plainly:** the current implementation is a *dispatch interface with emulated metadata*. It
is the right seam — one bit per instruction, `Config` untouched by workload content, both
front-ends sharing one hierarchy — and it is not a compiler.

## 2. Phase 3 — where the cycles go when Bulk loses

Three facts fall out of the columns before any commentary:

1. **The index stream is 5.0–32.5 % of the Bulk arm's DRAM reads** and its L2 hit rate is
   **0 %** (23 of 31 cells) to 0.05 % (the rest) [M: `cc1_l2_hits`]. It is pure added traffic in
   the sense that matters: essentially no line of it is ever served from cache.
2. **The read delta on the small-footprint SpMV traces is dominated by the index pass**
   (`qc2534`: +24 239 reads while 28 960 of its 111 686 reads are the index pass and only 318 are
   target lines — 99.7 % of the Bulk arm's reads on a 19.8 KiB footprint are *not* the data). On
   the sequential traces the delta is within 1 % of the index volume.
3. **`other` is large and is not attributable with M24-F's counters** — 62 % of Bulk's DRAM reads
   on `dubcova3`, 74 % on `qc2534`. This audit reports it instead of inventing a cause; §6.4.

Reading the dominant term:

* **`release slot-stall` is 60–97 % of the run** on `n3`, `dubcova3`, `n5`, `n1`: the release loop
  has translated runs but no free residency slot. The engine is waiting on its *own* outstanding
  requests, i.e. it is DRAM-throughput bound. That is the correct steady state for a streaming
  engine and it means these runs are not losing to "overhead" — they are losing to *traffic*.
* **`n1_seq8m` is the cleanest case**: 98 % of cycles in release slot-stall, the pool full
  (3 574 of 4 096 mean), 806 784 cycles of pool back-pressure, and an index pass of 8 192 lines on
  a stream SIMT already has at 92.9 % row hits. Bulk's own target ordering is *better* than SIMT's
  (row hits 92.9 vs 89.5) and it still loses 2.5 % because it pays 8 234 more DRAM reads for it.
* **`qc2534` / `bcsstk25` are the opposite shape**: the pool is nearly empty (13 and 24 entries
  mean), there is no back-pressure, and 27–29 % of the run is `drain`. These are L1-resident
  footprints where the engine's steady-state throughput does not matter; its per-line work and
  its tail do.
* The `organizer` column is the seal's sort, one visit per run (`bulk_org_runs`), charged at
  ~1 cycle per run.

### 2.3 Four candidate causes, scored

| cause | verdict | evidence |
|---|---|---|
| **A. Organisational overhead** (cohorts, translation pipeline, pool, buffers, sorting) | **Real but second-order on the long traces, first-order on the short ones.** | Organizer 75 080 / 484 783 cycles on `n3` (15.5 %), 820 209 / 3 937 942 on `dubcova3` (20.8 %), 232 051 / 881 339 on `qc2534` (26.3 %) [M]. Fanout 9–11 % on most. But removing *all* G6A–G6D structure (`bulk_org=0`, M24-H's ladder) leaves `n3` at 489 674 vs production 484 783 — i.e. the organisational overhead is mostly **paid for by the ordering it buys**, net ≈ 1 %. |
| **B. Redundant acquisition / processing** | **Not duplicate requests; one uncached pass.** | Bulk reads each index line exactly once (`bulk_idx_lines_done == bulk_idx_lines_req`, 8 192/8 192 on `n3`, 99 347/99 347 on `dubcova3`) with `cc1_l2_hits = 0` [M]. There is no repeated index acquisition, so the cost is not redundancy — it is that the pass never hits. |
| **C. Missing SIMT memory-system capabilities** | **The dominant mechanism.** | Bulk bypasses L1 (`Req::bypass_l1 = true` on every engine target, index and PTE request) and dedups only *inside* a window. SIMT's L1 absorbs 11 041 of 205 260 requests on `n3`, 619 106 of 1 948 034 on `dubcova3`, 161 531 of 455 640 on `qc2534`; its L2 then serves 123 076 / 60 205 / 3 190 more. | **D. Fundamentally unsuitable workload** | **True for 4 of 7, and it is a property the compiler can see.** | L1/L2-resident footprints (`qc2534` 19.8 KiB, `bcsstk25` 120.6 KiB, `dubcova3` 351.6 KiB) and already-sequential streams (`n1`, `n5`) are exactly the classes a selector should route to SIMT. `n3` is the one case that is genuinely hard: 906.8 KiB, random within a cluster, 87.5 % reuse inside a window. §4 of the selection design. |

**The honest one-line diagnosis:** on the long losing traces Bulk is DRAM-throughput bound and pays
for an extra uncached index pass; on the short losing traces it is bound by per-line work and by a
tail it cannot amortise. Neither is "extra calculations" in the arithmetic sense — the engine's
arithmetic is not what costs.

## 3. SIMT fairness audit

M20 flagged limitations in the SIMT model around coalescing, LSU, MSHRs and ports. Checked against
the current source:

| capability | modelled? | where / how | verdict |
|---|---|---|---|
| coalesce lanes to the same line | **yes**, per instruction | `system.cpp`: `cur_lines` dedups `tr_->acc[i].line` per instruction; `requests_generated` counts distinct lines (205 260 requests from 409 600 accesses on `n3`) | faithful for the intra-instruction case only; **no cross-instruction coalescing at the SM**, which is what WarpPool adds |
| merge outstanding duplicate requests | **yes**, at L1 and L2 | `l1_probe` MSHR join (`cc0_l1_joins` = 898 236 on `dubcova3`), `l2_probe` join (`l2.mshr_joins`) | faithful: a second request to an in-flight line waits on the same MSHR |
| cached index reuse | **yes, but not measurable per stream** | on M18/M21 traces the index accesses are ordinary trace accesses and go through the same L1; on **M23 graph traces the trace contains only targets**, so SIMT pays *nothing* for the index array while Bulk pays N×4 B. Every SIMT request carries client tag 0, so the model cannot report the index loads' own hit rate | **asymmetric by trace family** — see §6.3; per-stream SIMT attribution is unmodelled |
| realistic outstanding-load limits | **yes** | `R = 128` shared slots; `unissued_max` 122–126 on every losing trace (the pool is genuinely used); `lsu_pending` unset (0) in this configuration | faithful; the 4-way `warps_per_core` issue cap is modelled |
| cache and port constraints | **yes** | L1 256×4 @2 cy, L2 16 384×8 @4 cy, 2 banks × 4 096 rows × 1 KiB, one command/cycle, FR-FCFS | faithful; no bank-conflict or wire model in L1 (both arms equally) |
| independent warps hide latency | **yes** | 4 warps × 1 request/cycle, per-warp skip on refusal (`mem_->submit` false → try next held request) | faithful |
| **stores** | **no** | `MemorySystem` has no store path; `write_va` is host image setup | unmodelled for *both* arms |
| **value delivery on the SIMT side** | **no** | SIMT is a timing model: no register file, no result check | unmodelled; Bulk's values *are* checked (`addr_mismatch`, `engine_hash`) |
| **per-client translation attribution** | partially | `cc*` tags exist for L1/L2; `tlb0_*`, `l2tlb_*`, `walks` are aggregates | Bulk's extra walks cannot be separated from SIMT's without new counters |
| **Bulk's `cc0` DRAM stream** | no | 62–74 % of Bulk's DRAM reads on the SpMV traces carry client tag 0, which no engine request sets; the hierarchy's own return/fill path is not itemised | **unattributed — reported, not explained** |

**Nothing was weakened to favour Bulk, and nothing was strengthened.** Both arms share `R`, the
MSHR files, the caches, the walkers, the banks and the tick. The three asymmetries that exist all
favour SIMT: it pays no index traffic on the graph traces, its L1 is enabled while the engine's is
bypassed by construction, and the model has no store path (where the engine's ordering would be a
liability).

## 4. The index-acquisition question, traced

For `data[index[j]]`, seven stages. "Both" means the same code path serves both front-ends.

| # | stage | SIMT | Bulk | modelled? |
|---|---|---|---|---|
| 1 | index load | an ordinary trace access, coalesced per instruction | `.idx` stream: one line per 16 index words, fetched into a tiled ring (`idx_mode=2`, 64-line tiles, `idx_mshr=64`, `idx_reserve=8` slots) | yes, both |
| 2 | index cache lookup / coalescing | L1 then L2, with MSHR joins | L2 only (`bypass_l1`); one request per distinct line, no reuse across windows | yes |
| 3 | address calculation | none (the address *is* the trace's address) | fanout: `addr = data_base + idx[i]*data_bytes`, plus an independent re-derivation from the index image for `addr_mismatch` | yes (arithmetic is free in both) |
| 4 | translation | dTLB → L2 TLB → walker, shared | same path, plus a *translation-first* probe (`xlate_only`) that takes no residency slot | yes |
| 5 | target request generation | one per distinct line in the instruction | one per run after dedup + seal (`bulk_tgt_req_gen`) | yes |
| 6 | target data acquisition | L1/L2/DRAM | L2/DRAM, `bypass_l1` | yes |
| 7 | result delivery | none (timing only) | `val_[]`, `addr_[]`, verified against the index image | Bulk only |

**Does the index mechanism reduce traffic?** Measured answer: **no, it changes where the traffic
is accounted and it makes it uncacheable.**

* Volume: `idx_lines_done == idx_lines_req` in every cell (8 192 on `n3`, 99 347 on `dubcova3`,
  71 283 on `ogbn`), i.e. exactly one acquisition per line, no repeats, no prefetch [M].
* Cache: `cc1_l2_hits` = **0** in 23 of 31 cells; 1 325 / 405 / 642 / 5 446 / 1 in five of the
  remaining eight (≤ 0.05 % of the stream) [M]. A pass that is read once and never again cannot be
  helped by a cache, and it evicts what it passes.
* Consequence: the index bytes are unavoidable DRAM traffic for Bulk, and they are **5.0–32.5 %**
  of its reads. On the M23 graph traces the SIMT arm does not pay them at all; on the M18/M21
  traces it pays them too, but as ordinary accesses that go through its L1 and L2 (the model
  cannot separate their hit rate: SIMT requests are all client 0).
* The mechanism does buy something: it is what makes the engine able to translate *before*
  issuing, which is the precondition for the streaming release. It is a scheduling enabler, not a
  traffic optimisation.

**On the M24-F SpMV regressions specifically:** `qc2534`, `bcsstk25` and `dubcova3` all have
target footprints that fit in or near L1/L2 (19.8 / 120.6 / 351.6 KiB) and index shares of
0.96 / 0.86 / 0.30. Bulk reads the index array in full (28 960 / 15 766 / 99 347 lines) and misses
on essentially all of it, while its target reads collapse to 318 / 1 931 / 81 823 because dedup
already removed the repetition SIMT was serving from L1. The loss is **index pass + L1 bypass**,
in that order.

## 5. Why Bulk loses, mechanically

1. **The engine has no L1.** Every target request sets `bypass_l1`. On a cache-resident footprint
   that is the whole difference: SIMT serves 35.5 % of `qc2534`'s requests from L1; the engine
   serves 0 %.
2. **Dedup only spans one window.** A line touched in windows *k* and *k+1* is fetched twice by the
   engine; SIMT's L2 would have served the second. `n3` re-fetches 2.63 target lines per distinct
   line (38 166 requests over 14 509 lines); SIMT re-fetches 2.2× but pays only for the misses its
   caches did not absorb.
3. **The index pass is uncached and displaces the target set.** 8 192 lines of index on `n3` plus
   14 509 of target is 22 701 lines against a 16 384-line L2: the pass evicts exactly the lines
   the next window would reuse.
4. **The stream is already ordered.** On `n1_seq8m` the engine achieves *better* DRAM locality than
   SIMT (92.9 % vs 89.5 % row hits) and still loses, because ordering was not the deficit.
5. **The tail is not amortised.** On the 4 KiB–20 KiB footprints the run spends 25–47 % of its
   cycles after the last element retires (`qc2534` 414 706, `bcsstk25` 252 697). The audit could not
   attribute that tail with the existing counters and does not claim a cause.

## 6. Phase 6 — reconciling the prior numbers

### 6.1 M24-E's 1.21–3.86× "cohort admission" versus M24-H's 96-byte step

Both are right; they measure different comparisons, and neither is "cohorts are worth 3×".

* **M24-E** compares `bulk_org=8` against `bulk_org=7`. At org 7 the streaming release has **one
  cursor**: a dTLB refusal ends the cycle and admission stops on that page. Measured here again in
  the M24-H ladder: 7 → 8 is ×0.305 (`w4`), ×0.327 (`criteo_2k`), ×0.604 (`n3`), ×1.000 (`n1`).
  The gain is the removal of a *serialisation*, not the addition of locality.
* **M24-H** prices the cohort table at **+96 packed bytes** because at org 7 the pool, the PA buffer
  and the order arrays are already paid — the delta is the 8 × 32 B descriptor table minus the
  cursor state it replaces. That is the correct *marginal* cost, and 96 B for ×3.3 is the best
  trade in the design.
* **The two are consistent only if one also reports org 0** (no G6A/G6B at all): 0 → 8 is
  ×0.996/×1.121/×0.984/×0.990, i.e. **≈ neutral**. So the 264 KiB streaming stack, *including*
  cohorts, is worth ≈ 0 on the M24 panel and 8.5–11.2 % on the two long graph traces. Cohorts are
  worth a lot *given* the streaming pipeline exists, and the streaming pipeline is worth little
  without cohorts. Neither statement is "cohorts are worth 3× the whole engine".

### 6.2 What `bulk_org` 0 / 6 / 7 / 8 actually are

| value | pipeline | translated-first? | release order | pools |
|---|---|---|---|---|
| **0** | M6/M7: sealed window, `win_issue_sched` over the sealed order, cohorts over *pages of the window* | no | sealed (ascending line) | no G6B pool; `g6b_pa_capacity` unused |
| **6** | G6A: translate **all** runs, buffer their physical lines, then release (a barrier) | yes, with a barrier | P2 physical `(row,bank,line)` | `g6a_pa_capacity` 65 536 entries, one per run |
| **7** | G6B: stream — translate while releasing; one cursor over the sealed run array | yes, continuous | P2 physical | `g6b_pa_capacity` 4 096 |
| **8** | G6C/G6D: G6B with the admission walk replaced by P0's page cohorts (a refusal parks that page and another is tried) | yes, continuous | P2 physical | same pool; `page_cohorts` descriptors |

`org 0` is *not* "production minus cohorts": it is a different pipeline that keeps the M7 cohort
mechanism over the sealed window and has no physical buffer at all. `org 7` is *not* "production
minus everything G6 added": it keeps the PA buffer, the order arrays and the streaming release.
Only `org 6` differs from `org 7` by the barrier. The constructor enforces the valid combinations
(`bulk_org ≥ 2` requires the production map, `m24_dram_org = 0` requires org 7/8, org 8 requires
`page_sched` and `page_cohorts > 0`), and each cell echoes `bulk_org_policy`, so a mislabelled cell
cannot pass unnoticed.

### 6.3 The two trace families do not pay for the index array equally

* **M18/M21 traces** (the `w*` families and the four SpMV traces): the trace contains **index
  accesses as well as targets** — 409 600 accesses against 131 072 targets on `n3` — so SIMT loads
  the index array too, through the same L1 and L2 as everything else.
* **M23 graph traces** (`orkut_*`, `ogbn_uniform`, `criteo_2k`): the trace contains **only
  targets** (`accesses == tgt_acc`), so SIMT never loads the index array while Bulk pays its full
  N×4 B pass.

Consequence: on the graph traces Bulk's win is *understated* (it pays for traffic SIMT does not),
and on the SpMV traces the comparison is like-for-like. Any statement of the form "Bulk's index
overhead explains the SpMV loss" must not be transferred to the graph traces, where the asymmetry
runs the other way.

### 6.4 M24-F's per-client tags cannot attribute 62 % of Bulk's DRAM reads

`cc1` (index) and `cc3` (target) are exact and reconcile to the request counts
(`dubcova3`: 99 347 index requests → 99 347 misses; 101 584 target requests − 19 747 L2 hits =
81 837 vs `cc3` 81 823). The remainder, `cc0`, is 44 703 / 298 626 / 82 298 reads on
`bcsstk25` / `dubcova3` / `qc2534` and no engine request sets client 0. The model's own
return/fill path is not itemised. **This is an instrumentation gap, not a finding**: the audit
reports the split it can prove and labels the rest unattributed.

### 6.5 M24-D's `map3_s3` non-termination

`bulk_criteo_map3_s3` reaches the 500 M-cycle guard with every element done (294 912 / 294 912,
19/19 windows, last element at 3 292 976) and the ready pool pinned at its 4 096 capacity. M24-D
records it as a termination defect under one physical mapping. It is the same *class* as M24-G's
liveness edge — the engine's forward progress depends on a release being admissible, and when the
pool is full and every resident cohort is parked there is no state change that re-enables one.
Two independent triggers are now measured: `page_cohorts = 1` on `criteo_2k` (M24-G) and the map-3
page permutation on `criteo_2k` (M24-D). Both are on the same trace, the one whose pool reaches
4 096 in production. **Any M25 change to the pool or the admission policy must carry a liveness
test, not just a cycle comparison.**

## 7. What this audit hands to the other phases

| finding | consequence |
|---|---|
| the selector is metadata, not a compiler | Phase 4 must specify the *compiler* interface and the policy separately, and must not claim a compiler exists. |
| Bulk loses to cache reuse, not arithmetic | the first thing to fix is not the engine's logic but whether the engine should run at all on cache-resident footprints (Phase 4), and whether it can use L1 (Phase 7). |
| the index pass is 0 %-hit by construction | it is a fixed tax of `N·4 B` per kernel; the policy must gate on index share, and the architecture cannot remove it while translation-before-issue is required. |
| the organizer is 16 % of the engine and worth 0 on the production map | Phase 5. |
| two liveness edges, both on `criteo_2k` | Phase 7 must rank a liveness fix above any performance change. |
| 62 % of Bulk's DRAM reads are unattributed | the next milestone's first deliverable is a counter, not a mechanism. |
