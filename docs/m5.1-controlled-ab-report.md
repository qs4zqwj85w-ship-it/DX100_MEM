# M5.1 — Controlled A/B comparison: accelerator OFF vs ON

**Status:** the controlled A/B infrastructure is implemented and validated; the paired experiments are
run and reported below. No M6 mechanism (duplicate detection, cache-line deduplication, bank/row-aware
or clairvoyant scheduling) was implemented, and the accelerator was not redesigned.

**Answer to the milestone question, stated up front:** under an otherwise identical environment —
same configuration object, same materialized workload, same cache path, same translation hierarchy,
same `R = 128` residency budget, FIFO issue, no dedup — **enabling the bulk engine provides no
measurable benefit.** It costs **2.7 % more cycles on W1** and **46 % more cycles on W0**, moving
**6.3 %** and **25 %** more DRAM lines respectively (§8, §9). The residual differences that the earlier
milestone reported were **capacity and path**, not the accelerator: both are now equalized and the
advantage disappears. That is a result, and §9 separates the three mechanisms the design distinguishes.

Everything below is `[IMPL]` (measured with the commands in §1.3 / §7), `[A]` (modelling assumption) or
`[V]` (source-verified from `ref/vortex` @ `7300bc8`); `[PLAN]` marks what is deliberately absent.

page set by 4 096 pages and made the two arms incomparable.

## 3. Exact definition of accelerator OFF and ON

**A — accelerator OFF.** `Sim(cfg, trace).run(Mode::Baseline)`.

* No `BulkEngine` object is constructed (`Sim::has_engine() == false`, asserted).
* No descriptor fetch, no index stream, no address generator, no engine request buffer.
* The trace is consumed by the SIMT front-end: 4 warps × 4 lanes, coalescing by 64 B line, one slot
  per coalesced line request, ≤ 4 submissions per cycle, through the L1 → L2 → DRAM path.
* `desc_requests = index_requests = target_requests = 0` (asserted).

**B — accelerator ON.** `Sim(cfg, trace).run_bulk(workload)` with the same `cfg` and the same trace.

* One descriptor is fetched from memory, decoded and validated; `count = 16 384`.
* The index array is streamed: 1 024 line requests (16 four-byte indices per line).
* Each index value produces one target address; each target is one line request; `16 384` requests.
* FIFO issue, ≤ 4 submissions/cycle, no dedup, no reordering, no oracle, no special DRAM treatment.
* All three streams pass through the same L1 → L2 → DRAM path as A, hold slots in the same `R`, and
  are translated by the same TLB hierarchy.

The workloads are the same operation: A's trace *is* the sequence of `(data + index[i]·elem_bytes)`
accesses that B derives, because the index array is built from that trace (§1.1).

## 4. Residency-budget enforcement

One rule, applied to both front-ends:

```
residency  =  requests formed and holding a slot but not yet submitted   (unissued)
            + requests submitted to the MemorySystem and not yet filled  (issued_not_filled)

enforced every clock:  residency <= R = 128
```

* **A** allocates one slot per coalesced line request when it is formed (`free_slots`, `R/cores = 128`
  per core at 1 core) and releases it on completion; the peak is checked every cycle
  (`simt_peak_slot <= R`, `check("peak slot residency <= R")`).
* **B** allocates from its own pool of exactly `R` slot ids at request formation and releases on fill;
  `BulkEngine::tick` asserts `residency() <= R` every cycle (`bulk_residency_violations == 0`).
* The two arms never run concurrently, so they share **the rule and the capacity**, not a live pool.
  Both feed the same `MemorySystem`, whose in-flight list is the one an issued slot corresponds to.

**Measured, W1, l1 path, R = 128**

| | A (OFF) | B (ON) |
|---|---|---|
| peak slot-resident requests | **128** | **128** |
| peak outstanding incl. latch | 132 | 128 |
| coalescer input latch (`simt_staging_max`) | 4 | 0 |
| budget violations | 0 | 0 |

The 4-request gap is disclosed rather than hidden: A's coalescer holds the line addresses of the
instruction it is currently expanding, bounded by `lanes` (4), and it is **not** a queue — it is counted
(`simt_staging_max`), asserted `≤ lanes`, and it makes A's peak *larger* than B's, i.e. it favours A.

The budget binds in both arms: A's `simt_slot_full_cycles = 264 961` and B's `bulk_buf_full_stall =
275 663` (cycles in which the front-end could not form another request). At R = 8 both arms drop to
12 / 8 peak outstanding and lose ~4–5 % of throughput (§7), so the sweep is testing a live constraint,
not a label.

## 5. Cache and translation equivalence

**Cache path.** `mem_path` is one switch read by `MemorySystem`; a request bypasses the L1 only if the
switch says so, never because of which front-end issued it:

```cpp
bool path_bypasses_l1(bool req_wants_bypass) const {
  return path_mode_ == 2 || (path_mode_ == 0 && req_wants_bypass);   // l2 | native
}
```

With `mem_path = l1` (primary) every request from either arm probes `l1_probe(core 0, …)` and, on a
miss, one L2 probe. The identity that proves it — `l2_reads = (l1_reads − l1_hits − l1_mshr_joins) +
pte_fetches` — holds for both arms on both workloads (§6). Under the primary path B's L1 traffic is
non-zero and equals its request count (17 409), which the bulk run *asserts*: the M5 "engine has no L1"
check is applied only when the path really bypasses the L1.

`mem_path = l2` (both arms bypass, no cache in the path) is reported separately in §7; `mem_path =
native` keeps the historical per-front-end behaviour for realistic-system comparisons and is
**refused** by `run_ab` so it can never be mixed into a controlled result.

**Translation.** Identical by construction and verified at run time:

* same 16-entry / 4-way dTLB with 4 MSHRs and 2 parked replays, same 512-entry L2 TLB (8 MSHRs, 8
  requesters/entry, 4 cycles), same 2 walkers, 16-entry walk cache, Sv32 2-level walks at 150 cycles
  per level, and PTE fetches compete with data in the same L2;
* both arms translate the same virtual addresses for the data (identical VA layout, §1.1); B
  additionally translates its index array and descriptor, which is the accelerator's own cost and is
  counted separately;
* `pte_fetches = 2 × walks` in both arms;
* **walks: A = 512, B = 529.** The difference is exactly 17 pages = 16 index-array pages (64 KiB) + 1
  descriptor page, asserted in `ab_budget_equality`;
* capacity checks at run time: `tlb0_mshr_max ≤ 4`, `l2tlb_max_occ ≤ 8`, `walker_max ≤ 2` for both
  arms, and any violation would fail the run.

## 6. Traffic accounting

Definitions: a *line request* is a 64 B cache-line access formed by a front-end; a *DRAM read* is a
line the hierarchy actually fetched from DRAM; `dram_bytes = 64 × dram_reads` in both arms
(asserted). **There are no DRAM writes**: both workloads are read-only gathers, no store path exists in
the model (M4 §3.4), and this applies symmetrically. **Result/writeback traffic is not modelled** (§10.3).

| target-data line requests | 0 | 16 384 | — |
| **total line requests** | **16 384** | **17 409** | 1.063 |
| L1 reads / hits / MSHR joins | 16 384 / 0 / 0 | 17 409 / 0 / 0 | 1.063 |
| L2 reads / hits | 17 408 / 989 | 18 467 / 1 022 | 1.061 |
| DRAM reads | 16 417 | 17 444 | 1.063 |
| DRAM bytes | 1 050 688 | 1 116 416 | 1.063 |
| DRAM row hits / conflicts | 277 / 16 138 | 1 230 / 16 212 | 4.44 / 1.00 |
| TLB reads / misses | 16 384 / 15 835 | 17 409 / 15 860 | 1.063 / 1.002 |
| L2 TLB reads | 15 807 | 15 826 | 1.001 |
| page walks / PTE fetches | 512 / 1 024 | 529 / 1 058 | 1.033 |
| buffer-full stalls | 264 961 | 275 663 | 1.040 |

B's extra 1 025 line requests are its index stream + descriptor; it buys **no** reduction in target
traffic because target requests are one per element and the trace is a permutation (every element on
its own line). The 4.4× row-hit difference (277 → 1 230) is the index array being read sequentially;
it is not a DRAM optimization, and it did not prevent B from touching 1 027 more lines than A
(16 417 → 17 444) and finishing 2.7 % later.

### 6.2 W0 — regular streaming workload (κ = 1), l1 path, R = 128

| Metric | A (OFF) | B (ON) | B/A |
|---|---|---|---|
| total line requests | **4 096** | **17 409** | **4.250** |
| L1 reads / hits / **MSHR joins** | 4 096 / 0 / 0 | 17 409 / 0 / **12 288** | 4.250 |
| L2 reads / hits | 4 224 / 123 | 5 283 / 155 | 1.251 |
| DRAM reads / bytes | 4 101 / 262 464 | 5 128 / 328 192 | 1.250 |
| row hits / conflicts | 3 842 / 257 | 4 800 / 326 | 1.249 / 1.269 |
| TLB reads | 4 096 | 17 409 | 4.250 |

This is the informative case. A's coalescer turns 16 384 element accesses into **4 096** line
requests (4 contiguous lanes per instruction share a line). B has **no per-instruction coalescing**, so
it forms **16 384** target requests — 16 elements per line, 4× redundant. The L1 MSHRs absorb the
redundancy (12 288 joins, so DRAM traffic grows only 25 %), but B still pays 4.25× the request
formation, slot occupancy and TLB lookups: **44 773 cycles vs 30 573 (B 46 % slower)**. This is a
*request-formation* cost, and it is exactly what duplicate detection addresses — which is M6, not this
milestone.

### 7.2 Sensitivity — `mem_path = l2` (both arms bypass the L1)

| R | A cycles | B cycles | B/A |
|---|---|---|---|
| 8 | 282 028 | 294 052 | 0.959 |

Observations that hold in both:

* **Capacity helps both arms and stops helping at R ≈ 32–64.** A: 282 376 → 270 753 (−4.1 %) from

* **At every budget, on both paths, B is slower.** The gap narrows slightly as R grows (0.959 →
  0.974) because B's extra requests benefit more from a deeper budget, but never closes.
* B's requests and DRAM traffic are **R-invariant** (17 409 / 17 444), as they must be: capacity
  changes concurrency, not the work.

## 9. Speedup and traffic differences, and what may be attributed to what

### 9.1 The numbers

| | W1 | W0 |
|---|---|---|
| cycles ratio B/A | **1.027 slower** | **1.464 slower** |
| line-request ratio | 1.063 | 4.250 |
| DRAM-read ratio | 1.063 | 1.250 |
| walks ratio | 1.033 | 1.266 |

**No application-level speedup is claimed, and none exists in this model:** the model measures the
read side of a gather only (§10.3), and B is slower on both workloads.

### 9.2 Separating the three mechanisms (as the design requires)

| Mechanism | How it is isolated here | Measured contribution |
|---|---|---|
| **Additional outstanding-request capacity** | swept, R = 8 → 128, both arms at the same R | large and *shared*: A −4.1 %, B −5.5 %. This is capacity, not the accelerator, and it is now equalized. The M5 "128 vs 11" gap was entirely this |
| **Decoupled address generation** | the only difference left at equal R, equal path, equal translation, equal workload | **negative**: −2.7 % (W1), −46 % (W0). With the downstream hierarchy identical, generating addresses off-core removes no bottleneck — the binding resources are the 4-entry dTLB MSHR pool, the L1/L2 MSHR pools and the 2 DRAM banks, all of which B uses *more* than A |
| **Request organization** | not implemented (FIFO, no dedup, no reordering) | exactly 0 by construction. W0 quantifies the opportunity: B forms 4.25× A's requests, and 12 288 of them are absorbed by L1 MSHRs. Converting that into a gain is the M6 dedup/scheduling question — and it must be measured against *this* baseline, not against M5's |

**Explicit non-claims.** (i) The 4.4× DRAM row-hit ratio on W1 is a property of reading the index array
sequentially; it is not an accelerator gain and it did not produce a speedup. (ii) B's lower mean
latency on both workloads (1 524 vs 1 571 cy on W1; 219 vs 826 on W0) coexists with more total cycles —
per-request latency and throughput move in opposite directions here, so neither is evidence of an
advantage. (iii) B's lower issue-stall count is the same effect: fewer submissions blocked per cycle
because each request is resident longer.

## 10. Remaining modelling limitations

1. **The L1 is a per-core structure being used by a socket-level client.** Under the primary path the
   engine sits behind `core 0`'s 16 KiB / 16-MSHR L1, which its real architecture (design §4.4) does not
   have. The controlled requirement ("same path, no private cache") forces this; the native
   configuration is preserved for realistic-system work and reported separately (§7.2 is the closest
   controlled analogue: no L1 for either arm).
2. **`cores = 1` is enforced for the controlled run.** With S > 1 the SIMT arm would get S private
   dTLBs and S private L1s that the single global engine client cannot use; `run_ab` refuses that
   configuration rather than reporting it.
3. **No result/writeback path.** The LMEM tile write and copy-out are not modelled, so B's true cost is
   *understated*: adding them would make B slower, not faster. Excluded from **both** arms' comparison,
   which is the only defensible option without a shared write model.
4. **No store traffic anywhere.** Both arms are read-only gathers; `dram_writes = 0` on both sides.
5. **Translation latency is a parameter** (`walk_latency_per_level = 150`), so anything walk-bound is
   exact arithmetic on an assumption, not a hardware measurement.
6. **No RTL/SimX cross-check** (unchanged from M4): no RISC-V toolchain, no Docker, and this Vortex tree
   does not build on macOS. Every `[V]` claim remains a reading of the source.
7. **One gather family (`E0`), one descriptor.** B's multi-descriptor pipelining is not implemented, so
   this comparison measures the single-descriptor engine only.
8. **The four-request coalescer latch** (§4) is the only capacity term that is not identical between the
   arms, it is bounded by `lanes`, and it favours A.

## 11. Recommendation for the next milestone

**M6 should be scoped as an optimization milestone measured against *this* A/B harness, starting with
duplicate suppression, and it should not be launched without it.**

1. **Keep the controlled environment and the `run_ab` gates.** Every M6 arm must be compared at equal
   `R`, `mem_path = l1`, identical translation, and the same materialized workload. `run_ab` already
   refuses to run otherwise, and `ab_environment_identity` fails if a new setting escapes the signature.
2. **First mechanism: duplicate detection / line deduplication.** W0 shows B forms 4.25× A's requests
   for the same elements; W1 shows no reduction is available (permutation). The neutral-profile gate:
   with `ρ_dup = 0` the dedup arm must reproduce this milestone's E0 numbers exactly (17 409 requests,
   278 034 cycles, same completion hash) — the analogue of M4a for the mechanism.
3. **Second mechanism: issue-order policy** (bank/row-aware, from addresses already in hand), one
   policy per run, same `R` and same streams.
4. **Report capacity, generation and organization separately**, as §9.2 does. If a dedup arm wins, the
   win belongs to organization; if a capacity sweep wins, it belongs to capacity.
